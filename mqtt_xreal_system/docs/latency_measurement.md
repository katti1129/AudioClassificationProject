# 音の入力からAR表示までの遅延測定

## 測る区間

主要指標は、ReSpeakerの位置でサイレンの音が始まってから、Air 2 Ultraの表示に初めて警告が現れるまでの時間とする。音源の再生ボタンを押した時刻を開始にすると、再生機器の待ち時間も混入するため使用しない。

- 警告表示遅延：`最初にサイレン警告が見えた時刻 − サイレン開始時刻`
- 矢印表示遅延：`最初に立体矢印が見えた時刻 − サイレン開始時刻`

この2つは別に記録する。矢印にはDOA、頭部追跡、視野内判定が必要なため、警告と同時に出るとは限らない。視野外の音源は矢印ではなく旋回案内になるので、矢印遅延の基本実験は音源を正面に置く。

音源で音が発生した時刻から測る場合は「音源発音からの遅延」と明記する。マイクに届くまでの音の伝搬時間も含まれ、距離によって結果が変わる。

## 現在のログが測っているもの（2026-10-14のコード確認）

| 項目 | 実際の意味 |
| --- | --- |
| `inference_ms`／Jetson GUIの「遅延」 | バッファのコピー後からRMS・特徴量抽出・モデル推論・平滑化・判定まで。音の開始からの検知待ちや通信・描画を含まない。静音時は推論を行わない。 |
| MQTT `timestamp_ms` | JSONを作るときのJetsonの時刻。音声収集時刻やサイレン開始時刻ではない。 |
| CSV `timestamp` | Publish処理後にログへ渡す時刻。Beam Proでの受信・描画完了の記録ではない。 |
| Unity `Packet.ReceivedAt` | Beam Pro側の単調増加時計による受信時刻。JetsonのUnix時刻と直接引き算できない。 |
| Unityの`Present()`呼び出し | 表示データの更新。グラスの光学表示に実際に光が出た瞬間ではない。 |

参考コード：`Jetson_Final/app/legacy_gui.py`の`inference_thread()`、`Jetson_Final/mqtt/mqtt_bridge.py`、`Jetson_Final/telemetry/experiment_logger.py`、`BeamPro_Final/Assets/AmbulanceAR/Scripts/System/AmbulanceSystemController.cs`。

現在の主な設定は16 kHz・2048サンプルの音声ブロック（128 ms相当）、1秒のスライディング窓、最大5回の予測平均、サイレン閾値0.97・3回連続判定、各推論処理後の0.1秒待機、MQTT送信ループの既定間隔0.1秒。1秒窓があることは「必ず1秒待つ」という意味ではない。また、0.1秒待機は推論周期全体が0.1秒という意味ではない。実際の検知遅延は音源、窓内のサイレン割合、処理時間や直前の状態によって変わる。

## まず行う概測：外部カメラで音とグラス表示を同時記録

1. Jetson、ReSpeaker、Broker、Beam Pro、Air 2 Ultraを通常どおり起動する。実音声を使用し、Editor Simulationや疑似MQTT送信は混ぜない。
2. テスト用サイレンで一度推論を動かしてウォームアップする。初回推論の遅延は必要なら別条件として測る。
3. マイクとグラスの向きを校正し、音源を正面に置く。測定中は両者の向きを固定する。固定治具を使う場合も頭部装着版と同じ相対方向を保ち、追跡が有効であることを確認する。
4. スマートフォン等のカメラをグラスのレンズ越しに配置し、実際の警告表示が読めるよう調整する。撮影機器のマイクはReSpeakerの近くに置く。視野内の警告文と矢印が両方記録できることを先に試す。
5. 音声も記録できる通常の60 fps以上の撮影モードを使う。スローモーションは音声欠落や再生時間変更のある機種があるため、そのまま測定に使わない。
6. 無音を5秒以上続け、警告が消え、接続・追跡が有効な状態を確認してから同一サイレンを再生する。再生前の待機時間は少し変え、処理周期に固定されないようにする。
7. 例として、サイレンを10秒再生して10秒間を観測する。この時間は実験前に決め、全試行で統一する。最初の警告と最初の矢印の時刻をそれぞれ記録する。出なかった試行も削除せず残す。
8. 同一条件でまず30試行記録する。音源ファイル、音量設定、距離、背景雑音、モデル、Jetson電力モード、アプリ版、通信環境を揃える。

動画の音声波形からサイレン開始時刻を、映像から最初の表示時刻を読み取る。音声と映像には撮影機器固有の同期ずれがあり得るため、既知の同期イベントでずれを確認・校正する。未校正なら「外部動画による概測」として報告し、厳密な端末処理時間としない。

60 fpsのフレーム間隔は約16.7 ms、120 fpsでは約8.3 ms。これは映像の時間刻みであり、測定全体の精度保証ではない。実フレームのタイムスタンプを使用し、可変フレームレート動画を公称fpsだけで換算しない。音声トラックとの同期ずれ、撮影位置による音の伝搬差、表示開始の読み取り誤差も記録する。

## 厳密な測定が必要な場合

ReSpeakerの近くに置いた基準マイクと、グラス内の警告が表示される位置の光センサーを、同じ計測器・同じ時計で記録する。音の開始と光の変化の差を求めれば、JetsonとBeam Proの時計同期を必要とせず、実際の光学表示までを測れる。センサー設置・背景光・検出閾値の校正が必要。

Beam Proの画面録画やPCへのミラーリングは、それぞれの録画・転送経路を測ってしまうことがあるため、グラスの光学表示時刻と同一視しない。Unity公式でも`WaitForEndOfFrame`は画面表示前の段階と説明されているため、フレーム終端のログも光学表示の証拠にはならない。

- [Unity 6：WaitForEndOfFrame](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/WaitForEndOfFrame.html)
- [Android：Media projection](https://developer.android.com/media/grow/media-projection)

## 記録と集計

`latency_trials_template.csv`に記録する。全時刻は同一の測定タイムラインの秒数とし、音声と映像のずれを補正した場合は補正後の値を入力する。未補正なら`notes`にその旨を残す。

- `trial_status`：`ok`、`no_warning`、`no_arrow`、`invalid`のいずれか。実験前から警告が出ている、追跡喪失などで試行条件が成立しない場合は理由とともに`invalid`。単に未検知だった場合は無効扱いにしない。
- `audio_onset_s`：基準マイク位置でのサイレン開始時刻。
- `warning_visible_s`、`arrow_visible_s`：各表示を初めて確認した時刻。未表示なら空欄。
- `observation_end_s`：観測打ち切り時刻。未検知を「0秒」と記録しない。
- `warning_latency_s`、`arrow_latency_s`：それぞれの表示時刻から`audio_onset_s`を引いた値。
- `timing_method`：外部動画（音声映像同期校正の有無）／共通時計のマイク・光センサーなど。

条件ごとに試行数、警告表示成功数、矢印表示成功数、未検知数、無効試行とその理由を示す。表示が出た試行について平均、中央値、標準偏差、最小・最大を計算する。95パーセンタイルを示す場合は算出方法と試行数を併記し、30回程度では裾の推定が粗いことに留意する。異なる録画方式や音源条件を一緒に平均しない。

報告例（数値は実測して入力）：

> 正面・固定距離・同一音量のサイレンを30回提示した。ReSpeaker近傍の音の開始からAR警告の初回表示までを測定した。表示成功は○/30回、成功試行の平均遅延は○秒、中央値○秒、最大○秒であった。計測方法は○○、観測時間は各10秒である。

実機での光学表示測定は未実施。コード内の計測モードは別途追加した。[ソフトウェア遅延測定](software_latency_measurement.md)を参照。通常のMQTT v1形式は維持している。
